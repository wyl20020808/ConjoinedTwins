本轮修复用户实际使用的 `试玩追击与奔跑.cmd`，继续使用 `feature/pursuit-running-density` 任务工作区。未合并、推送、替换原项目或停止用户的游戏窗口。此前的 NPC 追击、两倍跑速、跑步动画和密集机关保持启用。

## 原因与处理

1. 本地展示原来在每个物理回调内刷新。主线程超时后，补算物理又重复刷新整套展示，形成持续追赶。现在本地和联机都只在画面帧提交一次最终展示；每帧最多补算三个回调，保留原 120 Hz 固定模拟和碰撞子步。上限只防止失控，实际降耗仍依赖下述优化。
2. 追兵格心检测反复分配表面字典、遍历全部地形，同一点还检查两次。现在普通地面只做支撑布尔查询，地形按纵向分桶；平台、渡船、吊桥、塌陷保留时间相关精确采样。
3. 身体、绳索和机关反复扫描全地图。现在用保守包络筛选候选，保持原索引顺序、完整旧/新绳段范围、扫杆运动余量，再执行原精确判定。工业机关使用全运动包络；未知与迎面移动类型不剔除。空间缓存随物理时刻、布局版本、数量更新，重试与读档显式失效。
4. 复用了另一个未合入工作区 `local-frame-stutter` 的展示刷新和类型索引思路，并补充空间筛选、联机展示处理和一致性检查；未修改该工作区，也未合并其分支。


可传 `--godot` 指定引擎，`--output` 指定工程外的新证据目录。默认输出到系统临时目录下带时间戳的 `ConjoinedTwins-performance` 子目录。

- 追击更新 p95 < 5 ms、最大值 < 40 ms；180 个画面循环内物理回调 170–270 次，双固定步平均 CPU < 14 ms，展示提交每帧至多一次。这是当前开发机的回归门槛，不能解读为所有硬件稳定 60 FPS。
- 资源预热后同位置节点增量 ≤ 8、对象增量 ≤ 64、静态内存增量 ≤ 4 MiB，材质增量 ≤ 4，网格缓存不增长；区块和任务均 ≤ 7。
- 超时、非零退出、脚本/引擎错误或泄漏告警均失败。结果附源码 SHA256；运行期间源码变化也失败。不允许仅看进程退出 0 就接受。
- 本规则已写入本任务分支的 `AGENTS.md`；后续合入 `test` 仍需要用户明确授权。

## 无界面验证的兼容边界

涉及救援、镜头、动态网格、资源生命周期或渲染设置的 Windows 迭代，还需运行原生渲染检查：

```powershell
python build-tools/check_rescue_native.py --output D:/ConjoinedTwins-task-temp/new-rescue-evidence --cycles 16
```

使用新的工程外目录；首次修复闪退用 `--cycles 128` 延长回归。该工具启动自己的离屏、无焦点窗口，保存引擎退出码、源码哈希、真实渲染器、逐轮资源计数、帧间隔和截图。崩溃、错误、泄漏、超时或源码变化都失败。`work` 模式记为 `deferred_by_work_mode`，普通 headless 检查继续；测试期间切换为 `work` 只终止此工具自己的进程。不能用截图、短暂启动或 headless 通过替代这个检查，也不能把离屏输入夹具算作玩家键盘验收。

最初多轮巡检暴露 Dummy 渲染器 RID 初始化错误，完整失败日志已保留。Godot 官方仓库记录了同版本无界面后台加载与 RID 分配的并发问题：[Issue #124139](https://github.com/godotengine/godot/issues/124139)；该版本 Dummy 网格存储也使用非线程安全 RID 容器：[源码](https://raw.githubusercontent.com/godotengine/godot/4.7.1-stable/servers/rendering/dummy/storage/mesh_storage.h)。结合本地错误栈，判断无界面资源加载存在同类风险。

资源队列在 `DisplayServer == headless` 时改为主线程按队列加载，真实窗口和 Web 保留后台 IO。兼容处理后完整巡检无引擎错误。CPU 稳态测量不包含同步导入耗时；真实窗口的异步加载、GPU 帧时间与显存仍待用户试玩/渲染验收，不能由本报告替代。
