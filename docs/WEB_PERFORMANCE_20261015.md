## 原因

1. 首包的 PCK 约 42 MB，原服务没有压缩该类型。引擎 WASM 则在每次新请求时动态压缩；本机首次请求也花了数秒。下载结束后仍有资源初始化、GPU 首次编译等长任务，不能只归因于隧道或网速。
2. 桌面浏览器沿用了桌面细节、动态森林阴影和七块预备区；菜单没有帧率上限。原测试菜单可达 141 FPS，消耗资源却没有提高游戏响应。
3. 120 Hz 固定模拟、每步三个子步中，多处对整关远处机关重复采样。地面缓存只保存最近一个时间，子步与预测时间交替查询会反复失效。无接触的直线绳段也会走完整切线接触链。
4. 浏览器追赶多个固定步时，每个物理回调都重建绳网格、刷新 UI 和更新音频；同一绘制帧发生重复工作。

## 修改

- 导出时为 JS、WASM、PCK 生成确定性的 gzip 副本；Caddy 优先读取预压缩文件。保留原文件与 ETag 校验，浏览器仍可自动更新。
- 网页单独采用最多 960×540 的 3D 渲染尺寸，UI 保持原始分辨率；关闭 MSAA 和大范围动态阴影，保留接触阴影，缩短远景细节距离，预备区从七块降至五块，帧率上限为 60。没有减少障碍、改变世界布局或删除关卡。
- 先检查保守运动包围盒，再执行原精确碰撞；绳索地面查询先处理附近几何，越界查询仍使用完整集合。地面多时间缓存最多 16 项，随模拟时间、版本或重试失效。
- 绳索求解在没有历史接触且直线避开所有最大截面时走等价快速路径；保留接触和跳跃截面预留逻辑。绳质点迭代内复用不变的绑定、阻尼和重力系数。
- 网页的画面、UI、环境音更新移至每次绘制一次，物理推进及联机帧处理仍保留原固定步。没有降低物理步长、子步数或求解迭代数。
- 旅程直接创建自己的模拟，避免先创建再丢弃旧道路模拟；网页版首屏不再预读旧白盒整套装饰模型。

## 第二轮：行进与机关附近卡顿

用户反馈第一轮仍频繁卡顿，截图位于第一章约 306 米。本轮继续使用同一任务分支，原始证据单独保存于 `web-performance-evidence/round2`，第一轮开局短测不能视为森林路段验收。

### 确认的问题与修复

1. `solid_sweep_clear` 在角色约束和二分回退中反复遍历整关实体。现在按类型索引，并以保守包围盒提前排除远处障碍；仍调用原精确扫掠判定。
2. 478 米出发后约 517 米的受约束站位，会触发大量绳长试算。旧实现每次试算都对十二个采样点查询整关地面。本轮先选取与绳段相交的平台，只在这些平台上采样；低于普通地面的特殊端点仍回退原算法。十二点插值、运算顺序与最终长度保持不变。
3. 工业机关的各分部、各时间片重复计算同一组绳段插值。现在复用插值，按单调弧长二分定位，精确碰撞逻辑保持原样。
4. 森林 MultiMesh 使用世界坐标变换、节点留在原点，整批实例共用宽大的包围盒，距离细节切换也参考错误的节点原点。网页版改为 32 米分区、局部实例坐标；导入网格直接复制并替换材质，保留索引和导入 LOD，避免重新提取整份顶点数组。
5. 首次森林资源上传和着色器绘制预热放在加载阶段，通过独立 32×32 视口逐资源提交。网页版长帧后最多追赶三个引擎物理回调，避免原先最多八个回调持续挤占绘制与输入；模拟内部 120 Hz、三个子步和十二次绳索迭代不变。持续过载时仍可能出现游戏时间放慢，不能把限制追赶等同于解决所有 CPU 开销。

### 测试方法和结果

浏览器测试仍为独立 Chrome headless、1280×720。诊断入口把角色放在指定位置，打开已经位于角色身后的门，再通过生产模拟的双人输入前进；不屏蔽当前危险，不自动通关。这是分段测试，不能算从起点合法抵达这些位置。最早未打开身后门的 306 米夹具测得 7 FPS，该夹具不代表实际通关后的同位置帧率，不用于性能收益对照。

| 区间/指标 | 观察结果 |
|---|---|
| 306 米无移动输入，第一轮包 | 41–45 FPS，约 211 万绘制面 |
| 修正森林批次后的同站位 | 35–47 FPS，约 40 万绘制面；仅降低面数不能保证 60 FPS |
| 最终代码从 306 米双人前进，存活采样 | 38–59 FPS，RAF 中位数约 20.8 ms、p95 约 27.8 ms；随后直行碰到合法危险而失败 |

主线程长任务仅统计进入运行阶段且角色存活的区间。最终 306 米及 798 米通过的样本中，该区间未记录超过 50 ms 的长任务；冷启动、首次进入诊断场景仍存在秒级阻塞，不能声称完全没有卡顿。浏览器测试期间机器上保留了用户自己的进程，系统负载未做强制隔离。

本轮没有操作用户正在玩的浏览器。Controller 独立测试、可见 GUI 和用户完整试玩仍未验收；新增诊断场景仅用于测试包，交付前移出项目。

补充隔离测试：Chrome 的 `--liftoff-only`（仅测试、不改用户浏览器）完成一次 25 秒采样，但帧率降至约 16–18，不作为交付方案；[V8 官方标志定义](https://chromium.googlesource.com/v8/v8.git/+/c495f9420f21340b554c56882a993a357eb5a3bf/src/flags/flag-definitions.h) 将其明确用于测试。独立 Edge 默认编译器完成相同 25 秒采样，后段约 54–60 FPS。这些有限样本不足以证明某个浏览器、编译器或硬件就是崩溃原因。最终代码保留默认浏览器运行方式。
